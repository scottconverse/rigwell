# Local review, triage and QA

Rigwell bundles `install-code-review`, `install-triage` and `install-qa`. Ask the agent to load the relevant skill. Each uses `InstallLocalService` to save an ordinary project automation under `.rigwell/automations`. Installation always asks for approval with the settings visible, including any result posting. An unattended run cannot install another service. Saving does not immediately run it; keep the daemon running for dispatch. Existing run history, reports, pause, editing and deletion controls apply in Automations and `ReadAutomation`.

Choose the GitHub repository (`owner/name`), existing local folder and run profile. Authentication reuses Code providers or a stored credential name. Never paste credentials into skill arguments. PR and issue sources can poll or use a signed webhook through the owner's tunnel. Push sources require signed webhook delivery and one exact branch. Rigwell does not register remote hooks automatically.

- Code review watches new/updated PRs or pushes, loads `review`, inspects the change and surrounding code and reports concrete severity/file/line findings. It does not apply fixes.
- Triage watches new issues, reads project guidance and searches issues, then suggests labels, duplicates and owners with reasons. It does not change labels, assign people or close issues.
- QA takes an explicit dev command, loopback HTTP(S) URL and changed flows. The run must verify that local HEAD matches the event's head SHA before executing code; a mismatch is reported as not checked. It loads `agent-browser`, starts its approved dev server, waits for readiness, interacts through accessibility refs and reports observations and omissions. It never automatically checks out incoming code. JavaScript evaluation requires an interactive approval. Owned server/browser cleanup applies even when the run fails; existing Session shutdown also releases background Execute jobs and browser profiles.

Results stay in local report files by default, ready for the user to inspect. Explicit `postResult: true` allows the automation dispatcher to comment on the verified source issue/PR, or the verified pushed commit. The model cannot choose a different destination. Existing redaction and uncertain-delivery handling apply. Branch deletion, tag pushes, wrong branches/repositories and malformed commit IDs do not dispatch. Admission uses receipt time rather than commit author time, so pushing an old commit is still a new event; delivery IDs are deduplicated.

Signed-in native clients can access the three installers through `Skill` and `InstallLocalService` and use Rigwell's ten browser tools through the existing request-scoped MCP capability. Actual Session approval and policy still apply, including mandatory approval for installation and browser evaluation. Native coding/process tools remain owned by the signed-in client; Rigwell retains session coordination. No new credential flow or agent loop is introduced.

Acceptance uses fake GitHub/provider/native clients, temporary projects and real headless Chromium. It verifies approved/denied installation, source filtering, review-skill execution, queued triage reports, source-bound comments, a changed form interaction and owned server/browser cleanup. This is not evidence of a live GitHub review, real subscription QA run or installed desktop behavior. GitHub's [push event contract](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push) defines branch refs and commit IDs; [commit comments](https://docs.github.com/en/rest/commits/comments#create-a-commit-comment) provide the source-bound push reply.
