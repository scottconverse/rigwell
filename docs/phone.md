# Phone access

Phone access is off by default. Open Settings > Phone access, select a specific LAN or Tailscale interface address and port, and confirm Enable. The daemon serves a separate HTTPS mobile page and WebSocket listener on that address. It does not bind every interface or open a firewall rule, install Tailscale, expose the existing local daemon token, or create a hosted relay. A fixed port preserves the browser origin across restarts; port 0 chooses a temporary port for diagnostics.

Choose Pair a device to display the QR code, one-time code, server certificate SHA-256 fingerprint and expiry. Open the QR URL on your phone. Before accepting the self-signed certificate, inspect its fingerprint in the browser's certificate details and compare it with the desktop. The fingerprint shown inside a newly loaded page alone cannot establish its identity. Browser certificate controls vary; use the browser's explicit certificate trust flow where required. Rigwell does not change operating-system trust automatically.

Enter a device name and pair within two minutes. Each code works once; generating a new code replaces the previous code. The URL fragment is removed from browser history on page load. The device receives a random credential stored only in this browser's origin-scoped local storage. Treat a paired browser as access to the computer's sessions, tool approvals and Workstreams. Use the device list to revoke a lost phone or a browser you no longer use. Revocation closes its active sockets. Clearing browser storage requires pairing again.

Open a session to read its transcript and send a message. Existing active sessions and Workstream members use their actual owned engines, with the same tools, permissions, subscription adapters and history. A phone view does not create another model loop. The mobile page can answer pending permission prompts and agent questions, stop a turn, view Workstream rosters, open member sessions and send messages with Later, Next or Now priority. Navigating between up to twelve sessions keeps their phone connections open. Disconnecting a view of a desktop-owned engine does not stop that engine. A phone-owned engine follows the existing daemon disconnect behavior, including parking a pending prompt for reconnection.

Enable notifications while open asks the browser's permission. Supported browsers can notify on session turn completion and requests for input while the page remains open. This is not a background push service; delivery also depends on browser and operating-system support.

The daemon stores configuration, its certificate/private key and hashed device tokens under `$RIGWELL_HOME/remote-access`, with private file permissions/Windows ACLs. Tokens expire after one year and are bound to the server certificate identity. A certificate is reused for its interface address, valid for 180 days and regenerated when within one day of expiry; a changed certificate requires verification and pairing again. Device credentials travel in an encrypted WebSocket subprotocol header, never a URL or cross-port cookie. Host/Origin checks, message/body/connection limits, pairing rate limits and a mobile-method allowlist apply. Administrative settings, credentials, fleet management and pairing methods remain unavailable to phone sockets. Pairing codes are memory-only and do not survive daemon restart.

Local acceptance uses the real daemon and self-signed TLS with fake providers and headless mobile/desktop browsers. Fixtures explicitly ignore their own untrusted test certificate; normal certificate verification rejects it. Checks cover one-time pairing, restart identity, expiration, revocation, wrong origins/hosts, blocked administrative calls, desktop engine continuity, question answers, approved/denied file writes, Workstream messages, browser notification calls and desktop enable/QR/device controls. Real phone certificate UI, LAN/firewall reachability, Tailscale and physical-device notification delivery still need hardware acceptance.
